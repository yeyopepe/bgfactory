## (a) Anotaciones funcionales

Fuera de alcance (heredado de la decisión del cambio 00036, no se reabre aquí):
- No se implementa CommonMark/GFM completo: solo el subconjunto de https://www.markdownguide.org/basic-syntax/ ya acotado en `description.md` (tablas, listas de tareas, resaltado, notas al pie, bloques de código con vallas ``` ```` ``` quedan fuera).
- No se implementa la sintaxis alternativa de encabezado con `===`/`---` bajo una línea de texto (decisión ya tomada al documentar el cambio, para no chocar con la regla horizontal `---`).
- No se admite HTML embebido suelto dentro del texto en formato Markdown (decisión de seguridad ya tomada; sigue tratándose como texto literal).

Limitación técnica conocida, aceptable bajo la política ya vigente de "el Markdown mal formado se muestra tal cual lo interprete el parser, sin avisar":
- El escapado con `\` (p.ej. `\*`) se resuelve como paso previo sobre todo el texto de entrada, antes de identificar bloques de código. Esto significa que una secuencia `\` + carácter especial que aparezca dentro de un bloque de código (en línea o indentado) también se interpretará como escape y perderá la barra invertida literal en el resultado. Caso extremo, coherente con la política ya aceptada de no validar el Markdown de entrada.

Dudas resueltas con el usuario durante el análisis de `description.md` (repetidas aquí por referencia): HTML embebido fuera de alcance, saltos de línea con semántica estándar (2+ espacios finales para `<br>`), encabezados alternativos fuera de alcance. No han surgido dudas técnicas adicionales durante el diseño de la solución.

## (b) Solución técnica

Todo el trabajo se concentra en reescribir `src/core/markdown.js` (`markdownToHtml`). No se toca `src/core/sanitizeHtml.js` ni `src/ui/componentRenderer.js`: el contrato de la función (recibe texto plano, devuelve una cadena HTML que luego pasa por `sanitizeHtml`) no cambia.

1. **Reestructurar `markdownToHtml` como un parser en dos niveles** (bloque y en línea), en vez de las sustituciones línea a línea actuales:
   - **Preprocesado de escapes** (`protectEscapes`/`restoreEscapes`): antes de nada, se recorre el texto original carácter a carácter sustituyendo cada `\` seguido de uno de los caracteres escapables (`` \ ` * _ {} [] () # + - . ! | < > ``) por un marcador interno (usando caracteres de control ``/`` improbables en texto de usuario), guardando el carácter literal aparte. Al final de todo el proceso, esos marcadores se sustituyen por el carácter literal ya escapado para HTML si hiciera falta (`<`/`>`). Se hace como primer paso para que esos caracteres no disparen ninguna otra regla (énfasis, enlaces, etc.) mientras se procesan.
   - **Extracción de definiciones de referencia**: se recorren las líneas (ya con los escapes protegidos, pero antes de escapar HTML) buscando líneas del tipo `[id]: url "título"` (o variantes `<url>`, comillas simples/paréntesis para el título); se extraen a un mapa `id → {url, título}` (id en minúsculas) y se eliminan del flujo de líneas — no generan ningún bloque visible.
   - **Escapado HTML** (`escapeHtml`, ya existente) aplicado línea a línea sobre el resto del contenido.
   - **Parser de bloques** (`parseBlocks`, función nueva, recursiva): recorre las líneas identificando, en este orden, regla horizontal (`***`/`---`/`___`, 3 o más caracteres iguales solos en la línea), encabezado (`#`…`######`, sin cambios), cita (líneas que empiezan por `>`, hasta 3 espacios de margen), lista (marcador `-`/`*`/`+` o `1.` con hasta 3 espacios de margen), bloque de código indentado (4+ espacios/1 tab de margen) y, si nada de lo anterior aplica, párrafo (líneas consecutivas no vacías que no empiezan ningún otro bloque).
   - **Citas** (`parseBlockquote`): agrupa las líneas consecutivas que empiezan por `>` (permitiendo continuación sin `>` en la línea siguiente inmediata, y párrafos múltiples separando con una línea en blanco seguida de otra línea con `>`), retira el prefijo `> ` de cada una y vuelve a invocar `parseBlocks` sobre ese contenido interior — así una cita anidada (`>>`) se resuelve solo por recursión, sin lógica especial adicional, igual que una cita que contiene una lista o un encabezado.
   - **Listas** (`parseList`): agrupa los ítems consecutivos del mismo tipo (numerada u ordenada; no distingue entre `-`/`*`/`+` para el propósito de mantenerlos en la misma lista, igual que hacía el código anterior). Para cada ítem, junto con el resto de la primera línea, recoge como parte del mismo ítem: líneas siguientes indentadas 4+ espacios (contenido enriquecido: párrafos adicionales, cita, código o lista anidada — se les quita esa indentación y se pasan recursivamente a `parseBlocks`) y líneas siguientes sin indentar que no empiecen otro bloque (continuación "perezosa" del mismo párrafo, comportamiento habitual al escribir un ítem de varias líneas sin indentar aposta). Si el resultado de `parseBlocks` para un ítem es un único bloque de párrafo, se descartan las etiquetas `<p>` de ese ítem concreto (lista "compacta"); si el ítem contiene más de un bloque (p. ej. párrafo + lista anidada), se mantienen (lista "suelta"), que es el criterio estándar de Markdown para uno u otro caso.
   - **Bloques de código indentados** (`parseCodeBlock`): líneas consecutivas indentadas 4+ espacios (o en blanco intercaladas), sin aplicar ningún formato en línea, envueltas en `<pre><code>` — el texto ya viene escapado para HTML del paso anterior, así que se muestra literal de forma segura.
   - **Párrafos**: se agrupan las líneas consecutivas y se unen aplicando la nueva semántica de salto de línea (ver más abajo), y el resultado ya combinado se pasa una sola vez por el parser en línea.
2. **Semántica de salto de línea dentro de un párrafo**: al combinar las líneas de un párrafo, si una línea (salvo la última) termina en 2 o más espacios, se marca ahí un salto de línea real (`<br>`, mediante un marcador interno que se sustituye ya al final, después del parseo en línea, para que no interfiera con las reglas de énfasis/enlaces); en cualquier otro caso, las líneas se unen con un único espacio (comportamiento estándar: un salto de línea simple no produce salto visual).
3. **Parser en línea** (`parseInline`, función nueva que sustituye a `applyInlineFormatting`), aplicado al texto ya combinado de un párrafo, al contenido de una celda de encabezado, o al texto de un ítem de lista suelto. Aplica, en este orden (usando un marcador interno para "proteger" cada resultado ya generado de que una regla posterior lo vuelva a tocar, y restaurándolos todos al final):
   1. Código en línea (`` `texto` `` → `<code>`, sin más procesado dentro).
   2. Imágenes por referencia (`![alt][id]`) e imágenes en línea (`![alt](ruta "título")`) → `<img src alt title>`.
   3. Auto-enlaces (`<https://...>`, `<correo@dominio>`) → `<a href>`, anteponiendo `mailto:` si es un correo.
   4. Enlaces por referencia (`[texto][id]`, usando el mapa de definiciones extraído al principio; si el id no existe, se deja el texto tal cual, sin enlazar — igual que la política de "Markdown mal formado se muestra tal cual") y enlaces en línea (`[texto](url "título")`).
   5. Combinaciones negrita+cursiva: primero las mezclas de delimitador distinto (`**_texto_**`, `__*texto*__`), luego `***texto***`/`___texto___`.
   6. Negrita (`**texto**` / `__texto__`).
   7. Cursiva (`*texto*` / `_texto_`).
4. **Reglas horizontales**: línea compuesta solo por 3 o más `-`, `*` o `_` iguales (con o sin espacios entre ellos) → `<hr>`. Se comprueba antes que la de lista para no confundir `---` (regla) con un ítem de lista, que siempre requiere contenido después del marcador.

No hace falta ninguna librería ni cambio en el build: sigue siendo una función pura sin dependencias, igual que hoy.
