## Descripción completa

Se quiere un script nuevo, independiente del script de build actual, que genere una variante del entregable jugable en la que solo exista el modo mesa de juego: sin el botón para entrar en modo edición, sin la barra de herramientas de edición, sin los paneles de gestión de componentes/recursos, sin las ventanas de configuración/edición ni las de exportar/importar partida. Todo lo que hoy es exclusivo del modo edición desaparece de esta variante; todo lo que es compartido con el modo juego (el modelo de datos de los componentes, el autoguardado, la mesa infinita, la interacción con fichas/dados/cartas, etc.) se mantiene igual que hoy.

No haría falta eliminar el 100% del código de modo edición en el proyecto fuente — el código sigue existiendo tal cual en `/src` para poder seguir generando también la build completa (mesa + edición) cuando se quiera. Lo que este script nuevo hace es limpiar, únicamente en la variante que genera, todo lo que es exclusivo de edición, no solo esconder el botón de acceso: hoy con solo esconder el botón el código de edición seguiría presente e incluido en el fichero final, solo que inaccesible desde la interfaz.

Para poder hacer esa limpieza de forma fiable, se van a introducir marcadores dentro del código fuente que señalen explícitamente qué partes son exclusivas del modo edición, de manera que el script nuevo sepa qué recortar antes de generar el fichero final. Lo que no está marcado como exclusivo de edición (compartido o exclusivo de modo juego) se queda intacto.

Preguntas de alcance resueltas con el usuario:

- **¿Este script toca el número de versión del proyecto?** No. El script no incrementa ni modifica la versión actual del proyecto — usa la versión vigente tal cual para nombrar su entregable, sin registrarla como una versión oficial nueva (eso sigue siendo exclusivo del proceso de versión ya existente).
- **¿Dónde se guarda el entregable de "solo mesa"?** En una ubicación propia, distinta de donde se guardan las builds oficiales versionadas, para que no se mezclen ni se confundan entre sí.
- **¿Se recorta también el CSS exclusivo de edición (paneles, ventanas, etc.)?** No por ahora: se mantiene todo el CSS tal cual, sin separar por marcadores. El único efecto de dejarlo así es que el fichero final pesa un poco más de lo estrictamente necesario, sin ningún efecto visible ni funcional (el CSS de edición nunca llega a aplicarse porque el HTML/JS de edición ya no está).
- **¿Se eliminan también los huecos vacíos en pantalla reservados para los controles de edición?** Sí, se eliminan también, para que la limpieza sea completa y no queden restos vacíos de la interfaz de edición.
- **¿Qué pasa a futuro, cuando se añadan funcionalidades nuevas a cada modo — cómo sabe el script qué recortar sin que alguien se olvide de marcar algo?** Prioridad confirmada por el usuario: lo importante es que el modo juego quede completo y correcto (que no falte nada de lo que necesita para funcionar); que se cuele algún resto exclusivo de modo edición en la variante de solo mesa no es crítico. Con esa prioridad por delante, el mecanismo de marcadores se diseña para que la mayoría de código nuevo exclusivo de edición se detecte solo (sin depender de que alguien recuerde marcarlo) — ver Apuntes técnicos para el enfoque concreto — dejando el marcado manual reducido a los pocos puntos donde código de ambos modos conviven en el mismo fichero.

Casos límite: si en algún fichero fuente un marcador de "empieza aquí lo exclusivo de edición" quedara sin su correspondiente marcador de cierre (o al revés), el script debe detenerse con un error claro indicando en qué fichero y marcador ha fallado, en vez de generar igualmente un entregable a medias o con restos de marcadores visibles.

Quién puede usar este script: es una herramienta para quien desarrolla el proyecto, se ejecuta a mano desde la terminal — no es una funcionalidad que use el jugador final, y no tiene relación con los modos/roles ya existentes dentro de la propia app jugable.

Sin componente visual: es una herramienta de generación de fichero, no añade ni cambia ninguna pantalla ni elemento de interfaz.

## Apuntes técnicos

- El script de build actual (`src/scripts/build.py`) empaqueta el entregable recorriendo el grafo de imports ES estático a partir de `src/main.js` (funciones `visit_module`/`IMPORT_PATTERN`); no hay ningún tipo de eliminación de código muerto más allá de esa alcanzabilidad. Por eso ocultar el botón de modo edición no basta por sí solo: `src/modes/edit/editMode.js` y todo el subárbol de `src/ui/*.js` que solo él importa siguen siendo alcanzables (y por tanto incluidos en el bundle) mientras `src/main.js` siga importándolos.
- **Mantenibilidad a futuro / mecanismo de detección (decisión tomada tras aclarar prioridades con el usuario — prioridad: que el modo juego quede completo y correcto; que se cuele algún resto de edición no es crítico):** en vez de poner un marcador manual de "fichero completo" en cada uno de los ficheros exclusivos de edición (~20 hoy, más los que se añadan en el futuro), el script debe calcular esa lista automáticamente por alcanzabilidad de grafo de imports, igual que ya hace `build.py` (`visit_module`/`IMPORT_PATTERN`) pero recorriendo el grafo dos veces: una vez arrancando desde el/los punto(s) de entrada de modo juego (`modes/play/playMode.js` + lo compartido de `main.js`) y otra vez arrancando desde el/los punto(s) de entrada de modo edición (`modes/edit/editMode.js`, `ui/editModeToggle.js`); cualquier fichero alcanzable solo desde la segunda pasada (nunca desde la primera) se excluye del bundle de solo-mesa. Con esto, un fichero nuevo de edición que solo importe código de edición se detecta y excluye solo, sin que nadie tenga que acordarse de marcarlo — el marcado manual (marcador de bloque inicio/fin) queda reservado únicamente a los pocos ficheros donde código de ambos modos convive literalmente en las mismas líneas (ver siguiente punto). Esto reduce mucho el riesgo de "alguien añade una feature de edición nueva y se olvida de marcarla": con el enfoque de grafo, ni siquiera hace falta acordarse, salvo que la feature nueva se meta dentro de uno de esos ficheros ya compartidos.
- Ficheros ya identificados hoy como exclusivos de modo edición (alcanzables solo desde la rama de edición del grafo, sirven para validar el enfoque anterior en la implementación, no es una lista cerrada ni a mantener a mano): `src/modes/edit/editMode.js`, `src/ui/editModeToggle.js`, y — solo alcanzables desde ahí — `src/ui/componentModal.js`, `src/ui/componentList.js`, `src/ui/componentTypeModal.js`, `src/ui/resourceModal.js`, `src/ui/resourceList.js`, `src/ui/batchUploadSummaryModal.js`, `src/ui/cardEditorModal.js`, `src/ui/cardTextBoxModal.js`, `src/ui/boardImageModal.js`, `src/ui/boardPatternModal.js`, `src/ui/diceFontModal.js`, `src/ui/imageAdjustModal.js`, `src/ui/elementSelectionModal.js`, `src/ui/exportSelectionModal.js`, `src/ui/importSelectionModal.js`, `src/ui/importConfirmModal.js`, `src/ui/importReportModal.js`, `src/ui/resizeHandle.js`, `src/ui/tableColumnResize.js`, `src/core/fileExport.js`, `src/core/importMerge.js`.
- Ficheros compartidos con mezcla de código de ambos modos en las mismas líneas (estos sí necesitan "marcador de bloque" inicio/fin manual, porque el grafo de imports no puede distinguir dentro de un mismo fichero qué línea pertenece a qué modo):
  - `src/main.js`: imports y llamadas a `renderModeSwitcher`/`renderEditToolbar`/`renderEditMode` (`ui/editModeToggle.js`, `modes/edit/editMode.js`), y la rama `mode === MODES.EDIT` de `renderActiveMode()`.
  - `src/core/persistence.js`: `buildComponentsExport`/`parseImportedComponents` son exclusivos de la barra de edición (exportar/importar), mientras que `saveState`/`loadState`/`readSeedState` son compartidos (autoguardado, usados también en modo juego).
  - `src/index.html`: contenedores `#edit-toolbar` y `#mode-switcher`.
  - Como estos son los únicos puntos de marcado manual y el mecanismo de grafo cubre el resto automáticamente, conviene además dejar como convención para el futuro (recomendable documentarlo en `ARCHITECTURE.md`/`STYLE_BIBLE.md` durante la implementación, a valorar por `ms-implement`) que cualquier funcionalidad nueva de modo edición se añada preferentemente en un fichero propio en vez de inline dentro de estos tres — así cae en el caso "se detecta solo" y no en el caso "hay que acordarse del marcador".
- Dado que la prioridad es que el modo juego quede completo (no que la limpieza de edición sea perfecta), no hace falta que el script incluya una comprobación exhaustiva de que no ha quedado ningún resto de edición en el bundle final — basta con que el fallo por marcador de bloque mal formado (ver "Casos límite" arriba) impida generar un entregable corrupto o a medias. Un resto de edición que se cuele por un marcador olvidado en el futuro es un defecto menor a corregir cuando se detecte, no algo que deba bloquear el script.
- `src/core/state.js` mantiene el campo `mode`/`MODES.EDIT`/`setMode()` sin cambios: es infraestructura compartida mínima (el propio modelo de "modo" de la app), no se considera código exclusivo de edición a recortar.
- El script nuevo NO debe escribir en `src/data/version.js` ni incrementar `CURRENT_VERSION` — debe leer la versión actual tal cual (mismo patrón de lectura que ya usa `build.py`) y usarla solo para nombrar su fichero de salida, en una carpeta propia distinta de `src/_output/versions/` (p. ej. `src/_output/gameOnly/`), con un nombre que la distinga de las builds oficiales (p. ej. `index-mesa-v{XXXX}.html`).
- Nota de contexto para el futuro (no bloquea esta implementación): el usuario prevé que la skill `ms-version` desaparecerá más adelante, y que cualquier lógica que hoy dependa de esa skill debería vivir directamente en los scripts de build. Revisado `.claude/skills/ms-version/SKILL.md`: hoy ya es un wrapper fino que solo ejecuta `buildCommand` (`python ./src/scripts/build.py`) y verifica el resultado — toda la lógica real (incrementar versión, generar el bundle) ya vive en `build.py`, no en la skill. No hay nada que migrar ahora mismo; el script nuevo de solo-mesa debe seguir el mismo principio, quedando autocontenido en Python sin depender de ninguna skill para su lógica.
- `.claude/ms-context.json` no tiene (ni necesita) ningún campo para este script nuevo: no forma parte del proceso de versión del framework (`framework.versioning`/`buildCommand`/`buildOutputPath` siguen apuntando solo a `build.py`).
