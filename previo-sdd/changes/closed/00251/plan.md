## (a) Functional notes

**Fuera de alcance:**

- No se prueba el redimensionado libre a cualquier proporción: ya lo cubre de forma genérica la batería de la funcionalidad 015 y no se duplica (así lo fija el `description.md`).
- No se tocan ni `src/ui/componentRenderer.js`, ni `src/ui/componentModal.js`, ni `src/core/state.js`, ni ningún otro código de producción: este cambio sólo añade `src/test/functional/tablero-simple.test.js`.
- No se crea ningún fixture `.json` nuevo: los casos que necesitan una partida (incluida la migración del nombre antiguo) construyen el array de componentes en el propio test y llaman a `loadComponents([...])` — que ya ejecuta `migrateTableroSimple` internamente. Esto evita un fichero de datos nuevo y hace el caso más legible.
- No se prueba el DOM interno de los sub-modales de fondo (`boardPatternModal.js` / `boardColorModal.js` / `boardImageModal.js`). El caso de "coexistencia de la configuración de fondo" se cubre a nivel de estado (manipular `properties.fondoTipo` y comprobar que las demás claves siguen intactas), no abriendo el sub-modal.
- No se comprueban literales de traducción: se asertan tipos de control (`input[type=number]`, `min`/`max`), estructura del DOM pintado (clases, nodos `<svg>`/`<polygon>`, estilos inline) y comportamiento, nunca `textContent` de etiquetas.

**Ajustes sobre lo que decía el `description.md`, tras verificar el código (para que el test aserte lo correcto):**

- El *clamp* del grosor de borde en la ventana de configuración (caso 8) dispara en el evento **`input`** (no `change`), acota a `[1, 20]` con `Math.min(Math.max(parsed, 1), 20)` y, ante un texto **no numérico**, deja `bordeGrosor = 2` (el valor por defecto), **no 1**. El caso 7 debe montar el componente y comprobar el DOM pintado, no inspeccionar `properties` tras cargar.
- El tablero en **modo juego** no recibe `onSelect`/`onToggleSelect` de `playMode.js`, así que ni lleva la clase `.board--selectable` ni reacciona a `click`/`dblclick` (a diferencia de carta y dado). El caso 9 aserta esa ausencia.

## (c) Architecture changes

Este cambio no modifica la arquitectura, pero durante el análisis se han confirmado inconsistencias entre `design/docs/architecture/003-component-types.md` (tabla `'tableroSimple'`) y el código real. `pv-do` debe aplicarlas al actualizar la documentación tras implementar:

- **Fila `fondoTipo`**: el tipo indicado es `'colorPatron' | 'imagen'`; el código admite **tres** valores (`'colorPatron' | 'imagen' | 'color'`, opción "color sólido" del cambio 00156). Actualizar la fila a los tres valores.
- **Añadir fila `colorSolido`**: `string (hex o vacío)`, default `#ffffff`. Color de fondo sólido cuando `fondoTipo === 'color'`; cadena vacía = fondo transparente. Hoy no aparece en la tabla pese a estar en `DEFAULT_BOARD_PROPERTIES` y tener rama propia en el render y en el modal.
- **Añadir fila `bordeActivo`**: `boolean`, default `true` (checkbox "Activar borde", cambio 00153). Si es `false`, no se dibuja borde (`border-style: none`); color y grosor se conservan en `properties`.
- **Fila `patronForma`**: dice que `'hexagonal'` (valor legacy) se interpreta como alias de `'hex-horizontal'` "on render **and normalized on re-save**". La normalización al re-guardar **no existe** en el código (`migrateTableroSimple` sólo cambia `type`; nada reescribe `patronForma`). Corregir a: alias resuelto **sólo al pintar** (`ui/componentRenderer.js`); el valor almacenado no se reescribe.
- *(Opcional, menor)* Fila `biselado`: "two tones derived from `bordeColor`" — precisar que el bisel pinta arriba/izquierda más claro y abajo/derecha más oscuro (`shadeColor(±0.35)`). Se puede omitir si se prefiere no tocar esa fila.

No hay que actualizar `design/docs/architecture/011-functional-test-framework.md`: su tabla "Test files" está declarada explícitamente como "not a live inventory" y `TRACEABILITY.md` (regenerado por `npm test`) es la fuente autoritativa del mapa funcionalidad↔test.
